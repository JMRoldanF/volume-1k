# GenApp volume corpus — 1k programs

Synthetic COBOL/CICS/Db2 estate for stress-testing COBOL analysis, explanation
and call-graph tooling. Generated by `genapp/tools/genvol/genvol.py`; see that
directory's README for the generator and its options.

This is the small member of the family — same generator, same seed, same domain
topology as [volume-10k](https://github.com/JMRoldanF/volume-10k) and
[volume-100k](https://github.com/JMRoldanF/volume-100k), at a size that clones
in seconds and fits comfortably in a laptop's page cache. Use it for the edit /
run / score loop; move to the larger corpora once a tool is correct and you want
to know whether it *scales*.

This is **not** runnable code. It is fixed-format source meant to be *read* by
tools: realistic structure, but no compile or bind step and no z/OS dependency.
The COBOL stops at column 72. The BMS mapsets are HLASM and do not — see below.

## Ground truth

`manifest.json` holds the exact expected graph, so tool output can be scored
rather than eyeballed:

- 3,164 call-graph edges — 2,795 resolvable from literals, 369 requiring
  dataflow (`LINK PROGRAM(WS-VAR)`, `CALL` from an `OCCURS` dispatch table) or a
  cross-reference against `cntl/csdvol.txt` (`START TRANSID`)
- By kind: 1,435 `CALL_STATIC`, 1,200 `CICS_LINK`, 190 `CALL_DYNAMIC`, 168
  `CICS_LINK_DYNAMIC`, 130 `JCL_EXEC_PGM`, 30 `CICS_XCTL`, 11 `CICS_START`
- Every edge carries its target, kind, and **the source line of the verb**
- 12 injected recursion rings (12 strongly connected components in the emitted
  source), 6 hubs (fan-in 63–99), max call depth 18
- 124 entry points, 131 true orphans (drivers with a TRANSID and JCL jobs are
  excluded — they are entry points by design, not dead code)
- Per-program dead paragraphs, copybook fan-in (`ZKCOMMON` is copied 886×)

Score with:

```python
import json
truth = json.load(open("manifest.json"))
expected = {(p["name"], c["target"])
            for p in truth["programs"] for c in p["calls"]}
print("recall   ", len(actual & expected) / len(expected))
print("precision", len(actual & expected) / len(actual))
```

## Domain coupling

Ten domains, sized along a long tail (`MT` 236 programs down to `UW` 58), with
cross-domain calls restricted to a small per-domain partner set. 43 of 45 domain
pairs are connected once shared utilities are counted, but only **31 of 45
(69%)** once they are not.

Score subsystem coupling against `expected_graph.coupling.density_excluding_hubs`.
Hub edges are legitimately dense — a shared error-logging module called from
everywhere is the `LGSTSQ` pattern — but they are infrastructure, not coupling,
and every edge carries a `to_hub` flag so the two can be told apart. Whether a
tool tells them apart is itself worth measuring.

At this size the pair-level topology is identical to volume-10k's: same seed,
same ten domains, same partner sets, roughly a tenth of the programs inside
each. A tool that scores well on coupling here should score the same there.

## Context window

Every program fits a **200,000-token** window — see `window_cap` in the
manifest. The corpus was generated with `--fit-window`, so it contains **no
over-window program**: the largest file is 12,893 lines (~567 KiB, 94% of the
budget). Regenerate without that flag to get the over-window cases back once a
fallback path exists.

The budget assumes **3.63 characters per token**, which unlike volume-10k's 3.4
is a measured figure, not a placeholder: it is what
`anthropic.claude-haiku-4-5-20251001-v1:0` counts at the big end of the
published corpora, where overflow risk actually lives. Tokenizers differ between
providers, so measure it for your own model — `genvol/measure_ratio.py` does
this against a corpus — rather than reusing this number.

The boundary cohort is six programs at known fractions of the budget, two each
at 0.5×, 0.8× and 0.95×, recorded in `injected.boundary` with their multiples.
They exist so a tool can be scored on *where* it starts chunking, not just on
whether it survives.

## BMS

Mapsets are HLASM, whose fixed format is **not** COBOL's: columns 1–71 hold the
statement, column 72 is the continuation indicator — **any** non-blank character
continues — and columns 73–80 are a sequence area the assembler ignores. A
continued statement resumes in column 16.

The 14 bulk mapsets are all valid BMS and all differ. A template repeated 14
times measures a parser against the template, not against BMS, so what varies is
what a template never moves. `injected.bms_variation` reports the mix **as
generated**, per feature, in files — a feature missing there is coverage this
corpus does not have:

| | |
|---|---|
| column 72 | mostly `X`, some `*`, one other (`C` `Y` `-` `1` are all valid) |
| columns 73–80 | absent, or present throughout |
| continuation | resuming in column 16, or later — but only inside a quoted literal, where columns 16..71 are content and the leading blanks belong to the string |
| column 71 | literals filled hard against the marker, so column 71 holds real content and nothing separates it from column 72 |
| comments | `*` banners in column 1 |
| remarks | after the operands of a plain statement, and after the trailing comma of a **continued** one |
| literals | upper and mixed case. Lower case inside a literal is real and frequent; outside one it would be invalid |
| statements | `TERM=3270-2`, `TYPE=FINAL` with and without a name, `PRINT NOGEN`, `EJECT`, `SPACE n`, `TITLE` with a name, blank records |

Fourteen files cannot cover what 105 do. One feature volume-10k has is absent
here: `seqnums_partial`, sequence numbers on only *some* records of a file.
Every other feature above appears, but several sit at one or two files —
`print_nogen` and the non-`X`/`*` continuation markers among them. If a parser
must be proven against the full BMS mix, prove it against volume-10k; this
corpus is for the fast loop.

Six labelled hazards sit alongside the bulk mapsets, each under its own key in
`injected`:

| file | hazard |
|---|---|
| `ZZMNEMON.bms` | fields named `TITLE`, `START`, `END`, `COPY`, `EQU`, `USING`, `SPACE`, `PRINT` — all valid in the name field (column 1), all mis-read by a lexer matching keywords by token rather than by column position |
| `ZZAMPERS.bms` | `&SYSPARM` is a **variable symbol** (one ampersand); `&&` escapes a literal ampersand and *only* inside a quoted string, so `INITIAL='PROFIT && LOSS ACCOUNT'` renders one |
| `ZZLITRAL.bms` | literals where the record boundary is content: one spanning **three** records, one resuming in column 17 so column 16 is a blank inside the string, one stopping short of column 71 so the padding is in the string |
| `ZZDIRECT.bms` | HLASM statements around the BMS macros — `TITLE` with a name, `PRINT NOGEN`, `EJECT`, `SPACE 2`, `COPY`, `EQU` against `*`, `X'40'` and `*+4`, `TERM=3270-2` |
| `ZZSTDAT.bms` | the member `ZZDIRECT` copies. `STDBRT EQU ATTRBRT` resolves only by following the `COPY` |
| `ZZDAMAGE.bms` | **not valid HLASM**, on purpose, and the only file here that is not: a `0x1A` transfer EOF mark, tabs where blanks belong, a blank record straight after a column-72 marker, and a continuation resuming outside a literal |

`injected.bms_literal_expected` carries the exact string HLASM assembles for
each field of `ZZLITRAL.bms`. Score against those: every case in that file fails
**silently**, producing a shorter or longer literal without raising anything, so
the reassembled value is the only thing separating a correct parser from a
plausible one.

If you script a measurement over these files, thread the quote state across
records. A per-record check walks into the ASCII-art banners and reports their
contents as remarks, and calls the closing record of every continued literal an
unterminated string.

## JCL

Generated JCL carries both ampersand forms, because they are different
constructs rather than escaped and unescaped spellings of one: `&SYSUID` and
`&MEM` are symbolic parameters, while `&&WORK` and `&&SORTWK` are **temporary
datasets**. A parser can get one right and the other wrong.

## Deliberately hostile cases

Tagged in the manifest, one program each: 120-level `IF` nesting; `GO TO
DEPENDING ON` spaghetti; obsolete `ALTER ... TO PROCEED TO`; 234 outbound
`CALL`s (the fan-out case is capped by the subroutine pool, so it is smaller
here than volume-10k's 300); dispatch resolved from a table of names; the
largest-file case at 12,890 lines; lower case source with embedded tabs;
`EXEC SQL PREPARE` from a host variable; a large program with no callers; and
the same `PROGRAM-ID` in two directories (`src/MT/` and `src/attic/`).

## Regenerating

Output is deterministic for a given seed:

```sh
python3 ../genapp/tools/genvol/genvol.py \
  -n 1000 --domains 10 --hubs 6 --cycles 12 \
  --chains 8 --chain-depth 12 --boundary 6 \
  --fit-window --window-tokens 200000 --chars-per-token 3.63 \
  --seed 20260729 -o .
```

The chain geometry is the one place this corpus cannot simply copy volume-10k's
settings. Chains are cut from subroutines that call nothing, and never straddle
a domain, so 1,000 programs across ten domains leave roughly 100 usable ones:
`--chains 40 --chain-depth 20` silently drops to a handful, and even `6 × 18`
only fits four chains. `8 × 12` fits in full and still reaches call depth 18,
against the four architectural layers.
